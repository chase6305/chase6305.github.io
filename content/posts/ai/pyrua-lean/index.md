**PyRUA-Lean 让机器人智能体把一次模型决策写成一段可执行 Python：程序调用原语、检查返回值、计算几何并做局部重试，模型再根据这段程序选择回传的结果继续规划。** 变量和辅助函数留在本次任务的运行时中，只有需要进入下一次模型判断的信息才进入对话。

名称展开为 **Python for Lean Robot-Use Agents**。这里的精简，体现在机器人智能体的模型调用与上下文交互安排上。

设想“把炉子上的黑碗放到盘子上”。接近碗、调用抓取策略、检查夹爪、抬升、修正放置位置，是一串相互依赖的操作。若每次都由模型读三张新图再选择下一步，模型调用与越来越长的历史会形成显著开销。PyRUA-Lean 将其中可由结构化返回值决定的部分放进程序，同时保留执行后的模型重规划。

## 1. 先区分三件事：planner、接口与执行原语 {#problem}

论文包含三组问题，不能把它们合成一个实验结论。

1. **固定 planner 和底层原语，改变交互接口。** GPT-6 Astra 通过 RPent 工具调用，或通过 PyRUA-Lean 写代码。700 个配对任务实例用于比较完整接口的成功率与推理开销。
2. **在另一套几何原语上评估一个完整智能体。** RoboDojo 使用作者编写的双臂运动与 RGB 感知库，不含 VLA；它与榜单上的完整系统比较。
3. **训练 planner 使用接口。** Qwen3.5-4B 通过任务成功奖励学习生成 cell，运动原语、感知服务和 VLA 权重保持冻结。

这里的 **primitive，原语**，是程序可以调用的一项能力。例如 `move_to` 执行一次末端运动，`segment` 返回目标分割与位置，VLA 原语执行一段语言条件动作。原语内部可以已经包含控制循环；一次 `move_to` 与一个仿真控制步并不等价。

**planner** 决定调用哪些原语、怎样组织它们、如何检查结果。接口则决定 planner 可以把哪些计算写成程序，以及哪些结果会进入它的下一轮输入。PyRUA-Lean 的主要贡献落在这两个层次的连接上。

与 [Jev 的类型化决策](/posts/ai/jev-decision-layer/)相比，这里允许 planner 输出更丰富的程序；与 [RRSI 的跨轮自改进](/posts/ai/rrsi/)相比，主对照实验明确关闭跨 episode 记忆。一次任务内保留 `bowl` 变量，和下一次任务复用经过筛选的经验，是不同机制。

## 2. 一次 Python cell 怎样形成两层闭环 {#execution}

### 2.1 外层：模型写代码，读反馈，再修订

模型获得任务卡、起始图像、API 参考和适用的操作说明，通过 `python(code)` 运行代码。一次 cell 可以包含多次原语调用。其执行结束后，运行时把打印、错误、末尾表达式和所请求图像送回模型，模型据此写下一段。

用三个对象记这件事：$E_k$ 是 cell 开始前的环境，$N_k$ 是 Python 命名空间，$c_k$ 是模型写出的代码。执行过程可写成：

$$
(E_{k+1},N_{k+1},F_k)
=\operatorname{Execute}(c_k,E_k,N_k).
$$

反馈 $F_k$ 被追加到模型可见历史；$N_{k+1}$ 中的数组、函数和中间结果继续留在运行时。这个表达式用于整理接口关系，不是论文提出的学习目标或状态估计公式。

### 2.2 内层：依据返回值决定下一步

下面是与论文主实验接口相符的简化结构；`bowl` 已由前一段定位。它展示控制流，不是一份完整任务脚本。

```python
approach = robo.move_to(pregrasp, gripper=robo.OPEN)
if approach.reached and not robo.done:
    result = robo.pi0_pick("pick up the black bowl", max_chunks=20)
    print(result)
print(robo.state())
if not robo.done:
    robo.show("agentview")
```

`approach.reached` 决定是否调用抓取；`robo.done` 决定是否继续动作或请求图像。这些分支在 Python 中执行，途中没有一个模型重新解释画面。若一个结构化标志不足以判断物体是否滑落，程序可以在这里结束并返回图像，让模型接手判断。

因此，合适的 cell 边界是**下一次需要模型判断的位置**。将所有动作塞进一个长循环，会让无法由现有反馈识别的错误一路传播。把每条赋值都拆成一次 cell，又会失去程序组合的收益。

### 2.3 持久状态保留什么，异常又改变什么

| 项目 | 在一次 episode 内的语义 |
| --- | --- |
| 变量与函数 | 前一个 cell 定义的变量、导入和辅助函数可在后续 cell 使用 |
| 原语返回值 | 先留在程序中；需要模型读取时再打印或选择性汇总 |
| 未捕获异常 | 结束当前 cell，将 traceback 返回模型；此前已经赋值的变量继续存在 |
| 已执行动作 | 保留已经发生的环境变化；Python 异常不会撤销一次抓取或移动 |
| 新 episode | 主实验不复用上次任务的经验或命名空间 |

“变量还在”也意味着**旧观测还在**。上次定位得到的碗中心不会因为机器人后来移动就自动更新。代码必须主动重读状态、重新定位，或明确使用一个仍成立的刚性几何关系。

论文 §3.1 还说明：主实验在后续动作原语开始前检查成功；外部 watchdog 负责整个 episode 的两小时上限。Codex CLI 在工具等待 300 秒后返回超时，**并不取消仍在运行的 cell**，后续 cell 会排队。这是该实验的执行设置，不能把“工具等待超时”当作动作已经停止。

### 2.4 图像进入程序，与图像进入模型，是两条路径

`robo.image(...)` 可以把图像读成数组，代码在数组上做颜色、几何或统计计算；`robo.show(...)` 则请求把相机图像附在反馈中供模型观看。读取数组不等于把完整数组序列化到对话里。

论文的精简反馈设置对应 `pure` 与 `on-demand`：执行痕迹仍可由系统记录，但不会全部自动回传给模型。固定版本库也支持更丰富的反馈模式，默认构造 `ArmToolkit` 时是 `rich` 与 `on-motion`，所以复现时必须显式核对配置。具体源码行为见[源码探针](#source-probe)。

## 3. 跟随一只碗：从已抓住到正确放置 {#placement}

论文 Figure 2 与附录 A 展示了同一个 LIBERO-PRO 实例：“把炉子上的黑色花纹碗放到盘子上”。代码智能体在前几个 cell 定位、接近、抓取、抬升和检查；最后一个放置 cell 根据几何计算目标，并在满足条件时下降与松开。

### 3.1 为什么不能把夹爪中心直接移到盘子中心

抓取时，末端参考点不一定与碗中心重合。设当前末端平面位置为 $\mathbf p_e^{xy}$，碗中心为 $\mathbf p_b^{xy}$，盘子中心为 $\mathbf p_p^{xy}$。在保持姿态且抓取刚性的平移近似下，需要把碗平移：

$$
\Delta\mathbf p^{xy}
=\mathbf p_p^{xy}-\mathbf p_b^{xy}.
$$

末端应接受同样的平移：

$$
\mathbf p_{e,\mathrm{target}}^{xy}
=\mathbf p_e^{xy}+\Delta\mathbf p^{xy}.
$$

这保留了末端与碗之间的偏移。若改为直接令末端平面坐标等于盘子中心，碗可能仍偏在一侧。涉及旋转或抓取滑移时，要重新估计相对变换，不能继续沿用这个平移公式。

### 3.2 放置高度要看碗底，而非只看碗中心

论文代码从可见表面的 world map 中选出一块碗区域，对高度做范围筛选，再取 2% 分位数作为碗底高度估计 $z_b$。设盘子表面高度为 $z_p$，当前末端高度为 $z_e$，预留间隙 $\varepsilon$，则：

$$
z_{e,\mathrm{target}}
=z_p+(z_e-z_b)+\varepsilon.
$$

括号中的 $z_e-z_b$ 表达“末端在碗底上方多高”。目标是让平移后的碗底到达 $z_p+\varepsilon$，而不是让末端本身降到盘子表面。

给一个可以手算的构造例子，全部使用同一世界坐标系，单位为米：

| 量 | 数值 |
| --- | --- |
| 当前末端 | $(0.40,\ 0.20,\ 1.12)$ |
| 当前碗中心 | $(0.42,\ 0.21,\ 1.09)$ |
| 盘子中心与表面高度 | $(0.45,\ 0.25,\ 1.00)$ |
| 碗底高度估计 | $1.08$ |
| 间隙 | $0.007$ |

平面修正为 $(0.03,0.04)$，末端目标为：

$$
\mathbf p_{e,\mathrm{target}}
=(0.43,\ 0.24,\ 1.047).
$$

复核它：碗中心平面位置随末端移动到 $(0.45,0.25)$；碗底随末端下降 $0.073$ 米，到达 $1.007$ 米，恰好位于盘子表面上方 7 毫米。随文脚本还检查整体平移坐标系后，这个关系保持不变。

**低分位数是经过筛选的可见点高度估计，不是物体真实底面保证。** 遮挡、错误分割、空点集和缺失深度都可能破坏它。论文代码里的像素区域、筛选区间、7 毫米间隙及运动参数来自这个实例，不能直接当作另一机器人或另一场景的标定值。

### 3.3 检查、下降、松开分别依据什么

这段程序的关键不只是一条几何公式：它先检查定位是否找到目标，再检查修正量与目标高度，下降后依据运动返回值决定是否松开，最后在任务仍未完成时请求图像。各检查说明的是不同条件：

- 定位成功表明感知模块给出了结果；不保证对象身份与坐标无误。
- `Move.reached` 表明运动满足其到达判据；不等于碗已经稳定放好。
- 主实验的成功标志来自 benchmark；它与程序自己打印“done”有不同证据来源。

完整 episode 中，工具调用智能体在第 17 次 LLM 调用完成任务，但全 episode 还包括后续文件与结束处理，总计 20 次调用、约 1.04M 输入 token。代码智能体在第 6 次调用完成，结束处理后总计 8 次、约 220k。两者达到成功的累计 token 分别约 816k 与 156k。**“到达成功时”与“整段 episode 计费”需要分别记账。** 论文主表采用后者，包含缓存输入与成功后的模型调用。

## 4. 为什么少一次模型调用，可能省掉不止一次反馈 {#token-accounting}

### 4.1 对话中的旧信息会进入后续输入

设一次任务共调用模型 $K$ 次；固定初始输入有 $B$ 个 token，第 $j$ 次调用之后新增 $d_j$ 个、会保留到后续输入的历史 token。在没有压缩或截断的简化模型中，第 $k$ 次输入为：

$$
P_k=B+\sum_{j=1}^{k-1}d_j.
$$

对所有调用求和，可以换一种顺序记账：

$$
\begin{aligned}
T&=\sum_{k=1}^{K}P_k\\
 &=KB+\sum_{j=1}^{K-1}(K-j)d_j.
\end{aligned}
$$

早期反馈会被后续多次读取，第 $j$ 次追加的内容被计入 $K-j$ 次。最后一次调用之后的输出，不会反过来成为此前调用的输入；若还有结束调用，必须把那次调用加入 $K$。

若每次追加量都为 $d$，历史这一项是：

$$
T=KB+d\,\frac{K(K-1)}{2}.
$$

这解释了两条相互配合的路径：**程序组合减少调用边界，选择性反馈减少边界之间携带的信息。** Python 数组仍保存在运行时，只回传几个统计量，还能避免将一大份中间数据加入每次后续输入。

主对照中，两者使用的 Codex CLI 保留完整对话，接近 272k token 时才对较早历史做摘要压缩。选择性反馈主要控制新增上下文，没有主动删除已经进入历史的内容。

这是一份条件明确的记账模型：实际请求还有消息封装、工具定义、代码和图像编码，历史也可能被压缩；输出推理 token 的计费与是否进入后续可见历史需要按服务记录区分。它不预测任意模型的真实 token 数，也不模拟 KV cache 的物理计算量。

### 4.2 亲自改变分组与回传量

下面固定同一串原语事件，比较三种反馈安排。初始输入采用构造值：工具调用为 2,000 token，代码接口为 2,400 token；每个事件产生的反馈量由输入指定。代码接口多出的 400 token 表示更长 API 参考的一种可能情况。

分组方案每个 cell 执行至多指定数量的事件；最后一组可以不足。保留比例逐组向上取整为整数 token。所有历史一直保留，不压缩；表格只计算输入 token。

{{< pyrua-accounting >}}

默认的 12 个事件逐次返回时为 103,200；每组三个、仍保留全部反馈时为 31,200；再将每组回传压到原反馈的 20%，为 13,920。这些数值由上面的累计公式构造，**不来自论文 benchmark，也不表示执行这些事件一定成功**。

试着将事件数改为 1：代码接口可能因为初始描述更长，反而消耗更多输入。再把保留比例改为 100%：分组本身仍可能节省反复读取历史的开销。程序可以独立验证的检查越少、必须交给模型判断的画面越多，能够合并的操作也通常越少。

### 4.3 token、账单、模型调用与墙钟时间要分别看

论文将**缓存输入 token 也计入 token 总量**，所以重复读取历史仍在统计中。账单却会区分缓存输入、非缓存输入、缓存写入与输出，因此省 65% 输入 token 不会自动变成省 65% 金额。

同理，代码 cell 可以执行更多原语和局部计算。少调用模型，不能直接推出机械臂用更短路径，也不能从调用次数换算出固定倍数的真实时间加速。论文主对照选择统计模型调用次数，原因之一是共享模型网关的单次调用时延波动很大。

## 5. 主实验：固定什么，又怎样计算结果 {#main-results}

### 5.1 700 个配对实例，1,400 段 episode

每个任务—种子组合，两种智能体各运行一段 episode。四组数据及预算如下，来自论文 Table 13：

| 分组 | 任务数 | 每任务种子 | 实例数 | 每 episode 模型调用上限 |
| --- | ---: | ---: | ---: | ---: |
| LIBERO-PRO | 40 | 5 | 200 | 40 |
| RoboTwin 2.0 | 50 | 5 | 250 | 40 |
| RoboCasa365 atomic | 18 | 5 | 90 | 40 |
| RoboCasa365 composite | 32 | 5 | 160 | 100 |
| 合计 | 140 | — | 700 | — |

两者均使用 GPT-6 Astra、high reasoning、相同任务实例和 RPent 原语实现，并关闭跨 episode 记忆。冻结的 VLA 分别为 LIBERO-PRO 的 $\pi_{0.5}$、RoboTwin 的 LingBot-VLA、RoboCasa365 的 RLDX-1；分割使用 SAM 3。提供操作指南时，两者获得相同指南，RoboCasa365 没有这类指南。

预算限制的是 **LLM 调用次数与整个 episode 的两小时墙钟时间**，没有让两者执行相同数量的原语。代码能在一个调用里完成更多原语，正是被评估的接口能力。研究结论因此应读成“相同模型调用预算下，完整接口的效果”，而不能改写成“相同原语执行量下只改变语法”。

| --- | ---: | ---: | ---: |
| LIBERO-PRO | 83.0% | 94.0% | 11.0 |

### 5.3 token 的收益主要来自更少调用

在同一共同成功集合内，用总 token $T$ 除以总调用数 $C$，定义按调用加权的平均输入 $\bar P=T/C$，则有记账恒等式：

$$
\frac{T_{\mathrm{tool}}}{T_{\mathrm{code}}}
=\frac{C_{\mathrm{tool}}}{C_{\mathrm{code}}}
\cdot\frac{\bar P_{\mathrm{tool}}}{\bar P_{\mathrm{code}}}.
$$

论文 Figure 5 给出的 LIBERO-PRO 分解约为 $2.55\times1.76=4.48$ 倍。RC365 atomic 则约为 $1.84\times0.83=1.53$ 倍：代码的**单次平均输入更大**，总输入仍因调用更少而下降。主表经过舍入，不能要求从其显示值复算出所有末位数字。

这项分解解释“账上省在哪里”，并没有单独识别“持久变量贡献多少、条件分支贡献多少、少回传图像贡献多少”的因果效应。把完整接口的组成部分完全拆开，需要另做对应干预实验。

## 6. 消融与失败：收益在哪些条件下成立 {#ablations}

### 6.1 只改成按需发图，不能复现代码接口的收益

论文在全部 200 个 LIBERO-PRO 实例上增加一个工具调用版本：不再每次动作自动返回三张图，而只在智能体调用相机工具时发图。结果来自 Table 14：

| 接口 | 全部实例成功率 | 共同成功子集的调用数 | 共同成功子集输入 |
| --- | ---: | ---: | ---: |
| 工具，自动发图 | 83.0% | 19.9 | 1.07M |
| 工具，按需发图 | 68.5% | 22.8 | 1.07M |
| 代码，按需发图 | 94.0% | 7.4 | 222k |

这一表的开销使用**三个版本都成功的 131 个实例**，所以不能将它的 222k 与主表 LIBERO-PRO 的 273k 当作同一集合的两次测量。

按需图像需要与程序检查、执行和重规划共同设计。这个消融支持“单独去掉自动图像不足以解释全部收益”；它没有测出选择性图像在代码接口内部的独立贡献，更不说明真实机器人应尽量不看图。

### 6.2 去掉 VLA，程序仍可组合已有动作

移除 VLA 后，代码还能组合接近、夹爪控制、分步下降和反馈检查。RoboTwin 的指南去除还显示出接口依赖性：无 VLA 的工具版本从 42.8% 升至 60.4%，代码版本从 68.8% 降至 66.4%。指南并非在每种接口上都有一致正收益。

### 6.3 只看成功任务，会漏掉什么

附录 E 把失败也纳入后，RC365 atomic 的工具与代码输入之比仅约 1.1 倍，平均费用分别约 0.94 与 0.96 美元，已经非常接近。代码初始 API 参考较长，失败 episode 又可能接近 40 次调用上限，这些成本会抵消一部分成功任务上的节省。

仅代码成功的 96 个实例中，52 个对应工具版本耗尽调用预算，另 44 个在预算用完前自行结束。后者包含程序化恢复与几何推理的例子，也包含同一个随机 VLA 原语恰好在一边成功、另一边失败的情况。每个实例每种接口只运行一次，不能把这 96 个都归类成“恢复逻辑更优”。

论文 Figure 3 还对已记录轨迹施加回溯 token 截止，比较达到工具版本最终成功率所需的 token 预算。这个分析比只看共同成功子集更广，但两者没有在预先给定这些 token 上限的条件下重新运行；智能体也没有机会根据新上限改变策略。

### 6.4 它确实写了什么样的程序

附录 C 统计主实验的 11,145 个代码 cell：45% 执行至少两个动作原语，19% 使一个动作依赖前一结果，30% 使用 NumPy 做计算，7% 调用前面 cell 定义的辅助函数，84% 请求图像。这些类别可重叠，不能把百分比相加理解为互斥组成。

84% 仍请求图像，说明这套系统并没有普遍放弃视觉反馈。主要变化是由程序决定**何时看、看哪个相机、哪些步骤先在本地完成**。在 RoboTwin 上，54% 的 cell 仍是“执行一步再看”，因此那一组节省调用的幅度也较小。

### 6.5 两个记录中的恢复例子 {#recovery-examples}

附录 D 的摩卡壶任务里，两种智能体都把壶掉到了桌上。工具版本四次重新调用 VLA 抓取，最后放弃；代码版本根据点云拟合壶盖平面，估计壶的倾斜方向，组合抓取和旋转，再把**壶底**对到炉圈上方。一次线性代数调用因半精度数组报错后，下一 cell 转换类型并继续计算。这同时展示了程序内几何与 cell 间修订，而不只是把已有技能重复多次。

另一个开柜门实例中，代码用三处把手位置拟合转动圆弧，再在一个 cell 内沿圆弧执行多次拉动，并在运动不到位或夹持异常时停止。工具版本每次模型调用只拉一小段，耗尽 40 次预算时门仍未完全打开；代码版本随后还有一次 VLA 调用，在第 34 次模型调用完成任务。这个例子包含解析运动与 VLA 的组合，不能将成功全部归给圆拟合。

这两段轨迹说明程序可以从基础观测中构造工具表没有直接提供的计算，并把检查接到后续动作上。它们属于特定实例的行为证据；前述完整对照、随机原语差异与失败成本，仍决定总体结论的范围。

## 7. RoboDojo：没有 VLA 和深度时，程序依据什么行动 {#robodojo}

### 7.1 换了一套机器人原语，也换了评测问题

RoboDojo 实验面向双臂 ARX-X5 桌面工作站，42 个任务分为 Generalization、Precision、Long-Horizon、Memory、Open 五个维度。每个任务按协议运行 50 段 episode，一个评测种子合计 2,100 段。Generalization 的 50 段包含标准场景与外观随机化场景各 25 段。

此处 planner 仍是冻结的 GPT-6 Astra，但使用作者自己的兼容端点智能体循环与几何原语库，**没有 VLA 原语，也没有现成的 `pick`、`place` 或 `grasp` 原语**。抓取由定位、移动到上方、沿线下降、闭合夹爪并检查开度等步骤组合而成。SAM 3 仍是学习得到的分割模型；“无 VLA”不等于所有模块都没有预训练。

| 原语类别 | 能力 | 返回信息如何参与程序 |
| --- | --- | --- |
| 运动 | `move_to`、`home` | 到达结果、附近可达姿态等 |
| 夹爪 | `set_gripper` | 是否夹到物体、开度等 |
| 感知 | `locate`、`segment`、`back_project` | 位置、顶部、平面轮廓、抓取朝向、参与观测的相机数 |
| 观测 | `state`、`show`、`image`、`camera_meta` 等 | 本体状态、图像及相机标定 |

运动库求解逆运动学，并执行抓取参考点的直线运动或关节空间摆动。模型仍需根据感知结果与这些运动能力编写程序；没有一个工具可以直接回答“整道任务已经如何解决”。

### 7.2 RGB 可以测几何，但依赖已知工作站与多视图约束

论文的 RGB 配置接收头部与两只手腕的三张彩色图，以及关节和末端状态；不读深度图、对象真实位姿或模拟器场景状态。库事先知道工作站的相机标定、机械臂安装位置与桌面高度，这些在 episode 间固定。

已知相机标定后，一个像素确定一条空间射线。若已知点处在某个平面，射线与平面相交就能得到三维位置；若物体有未知高度，仅把掩码投到桌面会将高度与平面位置混在一起。

论文描述的 `locate` 先由头部相机约束物体在桌面的平面范围，再结合能看到物体的腕部相机约束高度。因此，程序经常先移动手腕到物体上方，再测一次。返回值报告有几个视图同意；只有一个视图时，高度仍带假设，不能因为字段里有三维数字就当作直接测得了深度。

固定版本的 `robodojo_sight.py` 将这种约束写成掩码与几何体投影的匹配：尝试不同高度及适用的几何解释，把候选实体投回其他相机比较掩码，并处理机械臂遮挡。它没有假设“不同相机的掩码中心必定是同一个三维表面点”，也不能泛化为任意无标定单目图像都能恢复准确尺寸。[固定版本感知实现](https://github.com/DAGroup-PKU/PyRUA-Lean/blob/e754cf43c822b91f4728777a78071fa4e012c371/src/pyrualean/hosts/robodojo_sight.py)

### 7.3 运行期间没有任务成功标志

主对照实验可以检查 `robo.done`；RoboDojo 的 planner 在任务运行期间**读不到成功或进度信号**。它需要根据图像和机器人状态判断当前场景，benchmark 客户端负责执行动作并独立判定成功，达到成功或步数上限时结束 episode。

因此，把前文 `if not robo.done:` 的主实验程序原样搬进这个配置会违反接口契约。这里应使用运动与感知返回值组织程序，必要时回传图像，并由外部评测器记录最终判定。智能体自己调用 `finish(status="success")` 也不能代替 benchmark 的成功检查。

### 7.4 51.62% 与 50.52% 为什么都正确

RoboDojo 报告两种量：**SR** 是完整任务成功的比例，**Score** 则将过程奖励求均值后乘 100，允许部分阶段得分。榜单 Average 先在每个能力维度内平均，再对五个维度等权平均。

论文 Table 5 的 PyRUA-Lean 结果可整理为：

| 维度 | 任务数 | episode 数 | 成功数 | SR |
| --- | ---: | ---: | ---: | ---: |
| Generalization | 12 | 600 | 275 | 45.83% |
| Precision | 8 | 400 | 149 | 37.25% |
| Long-Horizon | 8 | 400 | 192 | 48.00% |
| Memory | 6 | 300 | 189 | 63.00% |
| Open | 8 | 400 | 256 | 64.00% |

按榜单方法，五个维度等权，得到约 **51.62%**。把全部成功 episode 直接相加，则是：

$$
\begin{aligned}
&\frac{275+149+192+189+256}{2100}\\
&\qquad=\frac{1061}{2100}\approx50.52\%.
\end{aligned}
$$

差别来自维度包含的任务数不同。较大的 Generalization 维度成功率偏低，按全部 episode 加权时占比更大。Score 58.20 又是另一项指标，不能将它解释成 58.20% 的任务完全成功。

该结果与**2026 年 10 月 9 日榜单快照**比较：当时最高排名条目 VPP2 的 Average SR 为 32.26%，两者相差约 19.4 个百分点。论文中的历史比较不表示这个名次在之后仍然不变；当前项目页与仓库还有其他更新，应按日期和配置单独阅读。

### 7.5 与同一 LLM 直接控制末端相比，改变了多个条件

论文引用的直接控制 GPT-6 Astra 系统 Average SR 为 22.48%，这里为 51.62%，约 2.3 倍。不过，两者除了动作接口，还同时在分割感知、推理 effort 与提示设计上存在差异。

直接控制版本由模型每次给一个末端目标；PyRUA-Lean 版本有分割、几何测量与逆运动学原语，并能写程序组合执行。这个结果说明**完整系统**的差别，不能当作只增加一个 Python 解释器的因果收益。

### 7.6 成功最多与失败最多的任务揭示什么

代码与几何组合擅长的任务包括按语言分类、排序和复用任务内记忆。论文中 `stack_blocks`、`cover_blocks`、`stack_blocks_by_language` 均达到 100%。但 `press_by_number`、`make_kong`、`insert_key` 等任务为 0%，而某些预训练策略在其中很强。

这些任务涉及当前反馈未报告的接触事件、精细配合或更复杂的交互状态。例如一次末端运动到达目标，不足以确认按钮完成了一次有效按压；夹爪到达孔口附近，也不等于钥匙插入并转动成功。作者没有对全部失败逐 episode 做出归因，不能仅从任务名断言每次失败的具体原因。

RGB 配置平均一段 episode 使用约 25.7 次 LLM 调用、750k 输入 token 和 9.0k 输出 token，持续约 12.7 分钟；论文网关上的平均费用约 2.4 美元。这套系统的能力与单个预训练策略的推理成本，也需要分别评价。

### 7.7 增加深度后，改善有限意味着什么

论文额外允许客户端提供深度图和相机矩阵，使 `locate` 与 `back_project` 能直接利用深度像素。这一配置不满足该榜单 agent 条目的 RGB 观测要求，因此**没有拿它与榜单排名比较**。

在相同种子上，Average SR 从 51.62% 升至 52.42%，Precision 从 37.25% 升至 41.00%。深度配置再评估三个种子，共 6,300 段 episode，Average SR 均值为 52.91%，种子间总体标准差为 0.35 个百分点。

这表明所测深度配置对这三个布局集合的整体结果较接近。RGB 配置只评估一个种子，不能把深度配置的标准差直接套作 RGB 的不确定性；有限平均提升也不能推出所有精细接触任务都不需要更准确感知。

## 8. PyRUA-Lean Coder：训练的是会写 cell 的 planner {#coder}

### 8.1 45 个实例，实际进行了 3,840 段训练 episode

训练从 Qwen3.5-4B 基础权重开始，全参数更新，不使用 LoRA；这轮 planner 训练没有先进行监督微调，也不使用示范数据。底层冻结 VLA 仍来自它自身的预训练与策略训练，不能据此称整个系统从未使用机器人示范。训练集为 LIBERO-PRO 的 goal、spatial、object 三个 suite，各取三个任务、每任务五个种子：

$$
3\ \text{suites}\times3\ \text{tasks}\times5\ \text{seeds}
=45\ \text{instances}.
$$

每次迭代抽取 16 个实例，每个运行 8 次 rollout，共 128 段 episode；30 次迭代合计 3,840 段，执行 60 个优化器 step。因此，“在 45 个实例上训练”描述数据覆盖，不是只运行了 45 次，也不是 45 个不同任务。

planner 读任务与 API，生成推理和代码，读取结果，再继续调用。运动原语、SAM 3 及冻结 VLA 仍负责实际能力。这个版本训练后是否也能驱动前节 RoboDojo 的无 VLA 几何库，论文没有评估。

### 8.2 成功奖励怎样形成组内优势

每段 episode 只有二元奖励：benchmark 成功为 1，失败为 0；没有对模型调用或仿真步数单独施加惩罚。同一个实例的 8 段 rollout 构成一组，奖励在组内归一化后形成优势。

为了手算，采用明确的总体标准差约定。若一组 8 段中 3 段成功，均值与标准差为：

$$
\mu_R=\frac38,\qquad
\sigma_R=\sqrt{\frac38\frac58}=\frac{\sqrt{15}}8.
$$

成功与失败的归一化优势分别为：

$$
\begin{aligned}
A_+&=\frac5{\sqrt{15}}\approx1.291,\\
A_-&=-\frac3{\sqrt{15}}\approx-0.775.
\end{aligned}
$$

三份正优势与五份负优势求和为零，但它们乘的是**不同生成序列的 log-probability 梯度**，所以总体策略梯度通常不为零。全成功或全失败时，没有组内奖励差异；随文算例将该组优势设为零。

这个总体标准差算例用于解释归一化。论文描述了组内标准化，但没有在正文给出标准差修正、epsilon 与具体 token 归约的全部实现；不能仅凭上述手算反推训练框架的每个数值细节。

### 8.3 非对称 clipping 与整段生成 token 的更新

令 $r_{i,t}$ 为同一生成 token 在当前策略和 rollout 旧策略下的概率比。用论文的上下剪裁范围，GRPO 的局部目标可以用以下形式理解：

$$
\begin{aligned}
\ell_{i,t}=\min\bigl(&r_{i,t}A_i,\\
&\operatorname{clip}(r_{i,t},0.8,1.28)A_i\bigr).
\end{aligned}
$$

优化器最大化这类代理收益，或最小化其相反数；训练实现还需要规定样本和 token 的汇总方式。论文将 episode 的优势作用到模型生成的推理与代码 token，未添加 KL 或熵项。工具返回的图像、原语执行结果并不是 planner 生成的动作 token。

例如优势为 +1、概率比为 1.4 时，收益取 1.28，继续提高这个概率比不再增加这项代理收益；优势为 −1、概率比为 0.6 时，收益取 −0.8。保守分支由优势符号与 `min` 共同决定，不能将整项更新简化成“把所有概率比强制限制在区间里”。随文程序用按优势符号展开的分段表达式独立检查这件事。

| 训练设置 | 论文 v2 配置 |
| --- | --- |
| 基础模型 | Qwen3.5-4B，全参数更新 |
| 每组 rollout | 同一实例 8 段 |
| 每迭代 | 16 个实例，128 段，2 个各含 64 段的优化器 step |
| 优化器 | Adam，学习率 $10^{-6}$，$\beta=(0.9,0.98)$，weight decay 0.1 |
| 训练长度 | 30 次迭代，3,840 段，60 step |
| episode 上限 | 24 个代码 cell、30 次 LLM 调用、25 分钟 |
| 生成上限 | 每次 4,096 新 token；每段至多 40,960；上下文 65,536 |
| 基础设施 | miles、SGLang、单节点 8 GPU，约 12 小时 |

基础设施故障导致一组缺失 episode 时，该组丢弃后重新采样；任务失败的零奖励仍属于训练数据。这一区别需要在日志与重跑策略中保留。

### 8.4 留出评测覆盖另外 655 个实例

训练只见过 45 个 LIBERO-PRO 实例。留出集包含其余 31 个任务的 155 个 LIBERO-PRO 实例（其中包含整个 long-horizon suite）、250 个 RoboTwin 实例和 250 个 RoboCasa365 实例。论文 Table 8 的结果为：

| 分组 | 实例数 | 4B 基础模型 | 27B 基础模型 | 训练后 4B |
| --- | ---: | ---: | ---: | ---: |
| 训练实例 | 45 | 37.8% | 64.4% | 71.1% |
| LIBERO-PRO 其余任务 | 155 | 13.5% | 38.1% | 37.4% |
| RoboTwin 2.0 | 250 | 14.0% | 20.8% | 52.4% |
| RC365 atomic | 90 | 52.2% | 65.6% | 76.7% |
| RC365 composite | 160 | 12.5% | 13.1% | 19.4% |
| 全部留出实例 | 655 | 18.8% | 29.2% | 44.1% |

训练后模型在合并留出集超过 27B 基础模型；**并非每一组都超过**，LIBERO-PRO 留出任务上 37.4% 仍略低于 38.1%。不同模拟器、机器人与冻结 VLA 均出现在留出评测中，支持接口使用行为的迁移，但没有建立任意机器人或任意原语库上的保证。

三种开源模型使用相同自有 agent loop、采样设置与预算：通常 40 cell，RC365 composite 为 100；墙钟上限为 90 分钟；上下文 65,536；每次最多 8,192 新 token。GPT-6 Astra 主实验采用另一 agent loop 和限制，所以 4B 的全体 45.9% 与 Astra 的 71.7% 可以作为参照，不能当作只改变模型大小的严格控制实验。

### 8.5 学到的是更合适的反馈节奏

Table 9 在留出实例上报告了一组很有解释力的行为：

| 行为或结束原因 | 4B 基础模型 | 27B 基础模型 | 训练后 4B |
| --- | ---: | ---: | ---: |
| 每次 LLM 调用的 cell 数，中位数 | 9.0 | 1.0 | 1.0 |
| 每 episode 请求图像数，均值 | 19.3 | 22.5 | 0.8 |
| cell 预算耗尽而失败 | 52.7% | 35.0% | 10.5% |
| 上下文溢出而失败 | 19.2% | 31.0% | 3.4% |
| 自行放弃而失败 | 6.9% | 4.6% | 25.2% |
| 墙钟超时而失败 | 2.4% | 0.3% | 16.8% |

图像均值不含所有 episode 都有的起始任务卡图像。基础 4B 常在一次回复里给出多个 cell，尚未看到前一个结果就承诺后面的动作；训练后通常写一个 cell，先读结果再继续。这也解释了**一次 LLM 调用与一个 cell 不能对所有模型都画等号**。

图像更少、上下文溢出更少与成功率更高同时出现，但训练并没有显式的 token 惩罚。论文所支持的是这些行为在该训练后模型中的变化，不能据此宣称学到了通用最优观测策略。

结束原因还发生了迁移：耗尽 cell 和上下文的失败减少，自行放弃与墙钟耗尽的比例上升。只报告“更少上下文溢出”，会遗漏模型仍有大量任务无法完成这一事实。

## 9. 固定源码：怎样确认自己运行的是哪一种接口 {#source-probe}

### 9.1 从代码入口追踪反馈路径

官方仓库支持持久 `cells` 和完整 `program` 两种代码入口，后者每次从新的程序命名空间开始、工作区文件可以保留。论文主要讨论的交互代码接口对应 `cells`，不能将另一入口的行为直接套入。

| 文件 | 适合核对的内容 |
| --- | --- |
| `arms.py` | `ArmToolkit`、持久命名空间、cell 计数、异常与反馈模式、图像附加 |
| `_robot.py` | 原语公共机制、调用记录、`show` 请求、结束保护 |
| `libero.py` 等机器人类 | 参数单位、坐标与四元数约定、结构化返回类型 |
| `openai_runtime.py` | 模型回复、多个工具调用的执行、图像与用量记录 |
| `runner.py` | 完整程序入口和 episode watchdog、宿主进程组的生命周期 |
| `sandbox.py` | 允许的导入、工作区文件访问与代码审计 |
| `hosts/robodojo_sight.py` | RGB 掩码与工作站几何约束下的三维测量 |

这些文件由不同入口调用。追踪时应同时记录 `arm`、`images`、`feedback`、原语集合、live-success 能力、预算和 agent runtime，而不是只记录“使用了 PyRUA-Lean”。[固定版本接口实现](https://github.com/DAGroup-PKU/PyRUA-Lean/blob/e754cf43c822b91f4728777a78071fa4e012c371/src/pyrualean/arms.py)

例如，LIBERO 的四元数顺序为 `[x,y,z,w]`，所核对的 RoboDojo RGB 类则使用 `[w,x,y,z]`。夹爪“闭合命令为 +1”与“测量开度越小表示越闭合”也属于不同字段。跨机器人迁移程序时，应读取该类生成的 API 参考，不能仅因方法都叫 `move_to` 就沿用全部参数语义。

### 9.2 当前 `show()` 不等于立刻冻结一帧

论文 §3.3 将请求点的信息记录与 cell 结束后的统一回传联系起来。固定源码中，`RobotBase.show` 实际先把相机名放进请求列表；`ArmToolkit._attach_images` 在 cell 结束时再读取该相机的最新 artifact。因此：

```python
robo.show("agentview")
robo.move_to(target)
```

不能据此认定返回的是**移动前**的画面。若需要中途的图像，应先读取并保存图像内容，例如在适用接口中将 `robo.image("agentview")` 的数组复制下来，之后交给 `display`。仅记住一个指向“最新图像”的路径或相机名，不一定保留旧内容。

随文源码探针使用记录对象和不含真实相机信息的字节标记，调用真实 `ArmToolkit` 与 `RobotBase.show`，检查“请求后再执行一步”及“先保存字节后执行一步”的区别。这验证的是**该提交的接口时序**，没有复现论文的机器人轨迹，也没有测量真实相机或设备延迟。

### 9.3 异常保留状态，成功保护阻止后续动作

另一个探针先赋值、执行一步、再主动触发除零错误。下一 cell 仍能读取先前变量，记录对象也仍停在执行一步之后的位置。这个实验对应“异常结束 cell，但不回滚 Python 之前的赋值和环境副作用”。

探针还验证：一个 cell 可以执行五次记录动作，但 cell 预算只消耗一次；预算用完后的下一段被拒绝。主实验式的成功结束状态也会阻止后续动作。这些保护不等于对代码中的所有几何假设、碰撞或物理稳定性作了证明。

代码执行的权限边界同样需要按实际宿主检查。仓库的 Python 限制与审计用于约束可见 API，但其源码明确指出进程内 Python 不能成为封闭的安全隔离。将它接到另一运行环境时，宿主隔离、动作权限和设备侧限制属于系统实现的一部分，不能从“用了 sandbox”这一名称推定全部性质。

## 10. 动手复算：从纸面数值到固定源码 {#reproduce}

### 10.1 第一阶段：只用标准库验证定义

下载 [interface_sanity.py](interface_sanity.py)、[参考输出](reference-output.json) 和 [说明文件](README.txt)，放到独立目录。运行：

```bash
python3 -B interface_sanity.py --check
python3 -B interface_sanity.py
```

检查包含：从各组样本数与舍入后的成功率恢复整数计数；分别计算五维宏平均与全部 episode 比例；用逐次拼接输入的方式独立核对累计公式；检查放置平移关系；穷举 256 种八段二元奖励组，对照高精度 Decimal 计算优势。

可以单独调用其中的放置计算。这个例子只计算构造目标，不连接机器人：

```python
from interface_sanity import placement_target

target = placement_target(
    eef=(0.40, 0.20, 1.12),
    bowl=(0.42, 0.21, 1.09),
    plate=(0.45, 0.25, 1.00),
    bottom=1.08,
    clearance=0.007,
)
print(tuple(round(v, 3) for v in target))
# (0.43, 0.24, 1.047)
```

先改变末端与碗中心的偏移，再检查移动后的碗是否仍落在盘子平面中心；再给全部点加同一个坐标平移，检查计算是否保持一致。最后故意输入 NaN 或缺少一个坐标，确认程序拒绝无效记录。完成这些步骤，比仅得到一次正确输出更有助于理解公式的适用条件。

### 10.2 第二阶段：验证官方运行时，不启动模拟器

下载 [probe_runtime.py](probe_runtime.py)。在可访问 GitHub 的环境中获取固定源码，再运行：

```bash
git clone https://github.com/DAGroup-PKU/PyRUA-Lean.git
git -C PyRUA-Lean checkout e754cf43c822b91f4728777a78071fa4e012c371
python3 -B probe_runtime.py --source PyRUA-Lean --output runtime-probe.json
```

探针先核对 Git 提交与将导入的七个源文件 SHA-256，再执行它们；不执行项目的包初始化入口，并主动禁止 NumPy、Pillow、PyTorch、模拟器等第三方包加载。它不安装依赖、不启动服务、不发送模型请求、不打开设备连接。临时代码 cell 写入临时工作区，结束后清理；`--output` 使用排他创建，已有同名文件会被保留并报错。

能够通过的范围是持久赋值、异常后的已发生副作用、图像请求与内容快照、cell 预算、默认反馈和成功停止保护。它不验证真实 `move_to` 的轨迹、SAM 3 分割、三维感知、VLA 或 700 个实例的成功率。

### 10.3 第三阶段：再进入带模拟器与模型的复现

完整实验需要匹配的模拟器、原语库、感知服务、冻结策略、模型 endpoint 与资产。按机器人分别使用官方文档，避免将不同 RPent 依赖栈混装进一个环境；论文使用的 RPent 提交也应固定。开源 planner 可以在兼容端点运行，但模型加载成功只证明服务能启动，不代表任务实例、cell 预算、反馈策略与评测判据已经对齐。

建议先取一个任务—种子组合，保存初始卡、全部生成 cell、原语调用记录、请求图像、模型用量和 benchmark 判定。先确认时间、单位、相机、成功信号与拒绝路径，再扩大到一个小的配对集合。最终比较要同时给出全体成功率、共同成功实例成本和包含失败的全部成本。

论文中的 4B 权重在写作时已能从官方模型页获取；论文 v2 中的“将发布”是当时的状态。是否存在新模型或新榜单结果，应以对应发布版本另行记录，不挪用 v0.1-4B 的数字。[官方 Coder 模型页](https://huggingface.co/DAGroup-PKU/PyRUA-Lean-Coder-v0.1-4B)、[运行文档](https://github.com/DAGroup-PKU/PyRUA-Lean/blob/e754cf43c822b91f4728777a78071fa4e012c371/docs/models/coder.md)

## 11. 从这篇工作提炼一个可检查的设计方法 {#design}

### 11.1 将确定的判断留在程序，将语义不确定性交回模型

原语已有明确返回值、下一步只依赖简单条件时，可以先组合进 cell。例如到达后才闭合夹爪、固定上限内重试、几何结果通过条件后才下降。需要识别新的物体姿态、解释滑落或重新选择操作方式时，让程序停止并返回足够的视觉证据。

关键问题是“当前反馈能否区分会导致不同后续动作的状态”。若夹爪开度无法区分抓到目标、抓到支架或卡住，减少图像会同时减少判断依据。要改善的是观测与控制的配合，不能只将“少发信息”设成唯一目标。

### 11.2 每段程序保留可追踪的观测与停止条件

局部重试应有次数、时间或状态进展的边界；没有到达、接触不明或位置不再变化时，应返回可诊断结果。一个“重试十次”的循环只限制次数，不自动证明第十次后机器人处于可继续的状态。

持久变量还需要对应自己的观测时刻和坐标约定。更换目标、相机或抓取姿态后，原来保存的对象中心、world map 和末端偏移可能失效。记录变量的来源，比在发生错误后只打印整份数组更容易追踪依赖。

这些原则可以与 [实时动作块调度](/posts/ai/real-time-chunking/)结合，但两者处理不同时间尺度：PyRUA-Lean 关注模型与原语交互边界，实时执行器仍需处理自己的控制周期、动作队列与反馈时效。论文主对照没有测出硬件实时控制或真实机器人恢复时延的结论。

### 11.3 给下一次实验设计一个清楚的对照

想区分三种机制，可以固定一个小任务集合，分别改变：是否在 cell 内组织条件链、是否保留跨 cell 中间结果、是否自动回传全部原语反馈。记录可执行的具体差异，同时保持 planner、底层原语、种子与成功判据可核对。

若只是把一个多步流程预先包装成新的工具，再与通用代码接口比较，原语的抽象粒度也改变了。这样的实验仍然有价值，但它回答的是“事先工程化的复合技能与在线程序组合怎样比较”，需要另起一项结论。

对随机 VLA，增加重复运行可帮助区分接口恢复与原语随机性。对真实机器人，还需要测量动作与相机时间戳、执行时延、失败后的恢复状态；这些不由模拟器成功标志或 token 均值替代。

## 阅读自测与验收 {#self-check}

1. **一次 cell 执行五个动作，算五次模型调用吗？** 不算；在一段回复只生成一个 cell 的设置中，它是一次调用、五次动作原语执行。开源基础模型可能一次回复生成多个 cell，因此仍需分别计数。
2. **异常发生后，前面的动作会撤销吗？** 不会；已赋值变量和已发生动作保留。下一段需要从真实当前状态继续。
3. **把末端移到盘子中心，为什么碗仍可能偏？** 因为抓取偏移；平移近似下，末端应接受“盘子中心减碗中心”的同样位移。
4. **论文提高了 14 个百分点吗？** 没有；442 到 502 个成功约提高 8.57 个百分点、相对提高 13.57%，标题取近似 14%。
5. **65% token 节省包括全部失败尝试吗？** 主表不包括；它在双方共同成功的 406 个实例上计算，且包含缓存输入与成功后的调用。
6. **按需发图为什么不必然节省总 token？** 若智能体因反馈不足多次询问或重试，调用与历史会继续增长；论文的工具按需发图消融就没有复现代码接口的收益。
7. **RoboDojo 可直接使用 `robo.done` 循环吗？** 论文配置不向 planner 暴露运行中成功信号，必须依据该接口的状态与图像组织执行，由外部客户端判定任务成功。
8. **RoboDojo 的 51.62% 是否等于 1,061/2,100？** 不等；前者五个维度等权，后者按全部 episode 计数约 50.52%。Score 58.20 还允许部分阶段得分。
9. **45 个训练实例是否只产生 45 段训练数据？** 不是；30 次迭代、每次 128 段，共 3,840 段 rollout，覆盖的是 45 个实例。
10. **八段优势加起来为零，梯度为什么可能非零？** 各优势乘不同的生成序列梯度；全组奖励相同才没有这个组内奖励差异。
11. **训练后 4B 是否在所有分组都超过 27B？** 不是；合并留出集更高，LIBERO-PRO 留出组仍略低，且本文没有测量任意新原语库的效果。
12. **源码探针通过，证明了机器人 benchmark 成功率吗？** 没有；它验证固定代码的运行时语义，未执行模型、模拟器、感知服务或真实动作。

完成阅读后，可以交付三个具体结果：一份明确 cell 边界与停止条件的抓放程序草图；一份能同时给出成功子集与全体尝试成本的记录表；一个可说明所测配置、聚合分母和失败来源的小规模对照。这些结果分别对应程序理解、统计记账和实际评估，不能相互代替。
