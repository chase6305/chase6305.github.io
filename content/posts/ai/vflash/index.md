视觉语言模型可以预测抓取点、物体框和未来轨迹，但把这些几何量逐个翻译成文本 token，会让输出越精细、生成越慢。**VFlash 将完整视觉基元作为并行预测单位，同时保留文本的验证式推测解码，再把几何计划送回冻结 VLM，提取下游控制所需的特征。**

本文依据 [NVIDIA VFlash 项目页](https://research.nvidia.com/labs/lpr/vflash/)及其[技术报告](https://research.nvidia.com/labs/lpr/vflash/assets/paper/vflash.pdf)，本轮核对日期为 2026-11-08。另一个指定来源 [Eagle/Embodied](https://github.com/NVlabs/Eagle/tree/783f656d127ee498137b5ff52603ce36c292d317/Embodied) 在此版本发布的是 **LocateAnything**，不是完整的 VFlash 机器人系统。它提供并行框解码的相关实现；不能直接把其中的安装命令当作 VFlash 的部署流程。

## 阅读路线

先看[视觉基元](#primitive)和[解码流程](#decode)，再看[控制接口](#control)与[实验口径](#results)。[源码对应](#code)说明 Eagle 中真正可用的能力，[接入检查](#integration)整理从几何输出到机器人控制还缺哪些契约。

## 1. 为什么几何输出需要不同的解码单位 {#primitive}

普通自回归生成按 token 推进。假设轨迹有 N 个点，每个点需要 d 个坐标，再加分隔符，输出长度会随 N 和 d 增长。坐标之间存在结构：同一框的四条边、同一轨迹的相邻点，都是相互关联的几何量。

固定长度的推测窗口不一定与这些边界重合。一段窗口可能只包含半个框，下一段又包含剩余坐标和下一个对象的标签。VFlash 的关键是让模型在训练和推理时都知道完整基元的起止与每个位置的角色。

### 1.1 边界对齐与位置对齐

边界对齐回答“这一块预测什么完整对象”；位置对齐回答“块中第几个位置代表哪个坐标”。例如十个三维路点需要三十个坐标位置，但整个序列还可能包含开闭标记，所以不能把三十当作完整序列的 token 数。

普通文本数字宽度不固定：一个坐标可能分成多个子词 token，使后续轴的位置偏移。官方方法使用专用坐标 token 或固定宽度数字字段，让路点、轴和分隔符的位置可预先确定。不同编码方案不能共享一个未经确认的长度公式。

### 1.2 并行不意味着没有几何依赖

VFlash 的 drafter 有五层非因果 Transformer。非因果注意力允许块内位置相互交换信息，而不必等待前一个位置先被采样出来。训练对标注几何使用 token 交叉熵，目标 VLM 在 drafter 训练阶段保持冻结。技术报告第 2.4 节还说明，先以 next-token 监督将 AR VLM 适配到空间输出格式，再冻结目标并训练 drafter；因此“冻结”不表示目标模型从未经过任务适配。

这种并行预测并没有强制每个点独立，也没有直接证明轨迹满足碰撞、速度或动力学约束。它首先解决生成效率和几何预测质量的问题。

## 2. 从观测到基元，再到上下文更新 {#decode}

整个过程可以分为四步：

1. 图像和指令进入目标 VLM，完成视觉编码与上下文预填充。
2. 结构化工具调用声明输出长度，基元类型确定坐标布局。
3. drafter 根据冻结目标模型的上下文特征，一次预测完整基元。
4. 将生成的基元送回目标模型，更新缓存并取得后续解码或控制需要的隐藏状态。

第四步尤其容易被忽略。一次并行草拟并不等于整个系统只运行一次模型：下游需要的是编码了计划的 VLM 特征，仍要支付这次目标模型处理的成本。

### 2.1 文本和几何采用不同接受规则

项目页给出的文本路径使用十六位置块，其中一个是已接受锚点，十五个是候选。目标模型一次验证后保留最长匹配前缀，再给出自己的下一个 token。

视觉基元则不要求逐 token 重现自回归目标。它直接学习标注几何，因此可能产生不同于目标模型、但在空间误差上更好的输出。附录 B 的基准 drafter 具有约 537M 可训练参数，共享冻结目标的输入嵌入与输出投影；“轻量”是相对目标模型而言，部署时仍需计入这部分权重、特征与缓存。**不能把视觉路径描述成保持原目标分布完全不变的普通推测解码。**

反过来，“不要求逐 token 一致”也不表示完全不使用目标模型：冻结上下文和后续特征回填仍来自目标模型。文本验证、几何预测和特征提取承担三个不同职责。

### 2.2 直接接受仍然需要校验与失败回退

技术报告第 2.5 节将接受条件定义为结构校验；对框，还加入 LocateAnything 的空间置信度保护。通过校验的基元无需与 AR 目标逐 token 相同，但校验失败时会调用受约束的目标 AR 重生成。轨迹不保留草稿前缀；框可以保留第一个不确定坐标之前的部分。

因此，视觉路径包含“直接接受”和“失败回退”，而不是无条件信任所有并行预测。格式校验能检查合法坐标与分隔符，不能取代碰撞、动力学或真实环境可执行性检查。

论文表 3 的框实验将这个取舍展示得很清楚：

| 数据集与方法 | 平均 F1（%） | 框／秒 |
| --- | ---: | ---: |
| COCO，AR | 48.68 | 3.15 |
| COCO，VFlash 直接接受 | 41.32 | 5.96 |
| COCO，VFlash 加 AR 回退 | 47.79 | 8.76 |
| Dense200，AR | 60.10 | 6.73 |
| Dense200，VFlash 直接接受 | 39.09 | 22.66 |
| Dense200，VFlash 加 AR 回退 | 61.78 | 17.46 |

直接接受的高吞吐可能伴随明显质量损失；项目页所说的框质量接近 AR，应结合回退配置阅读。COCO 中回退版本的报告吞吐高于直接版本，也不能推出回退本身没有成本：输出数量与生成路径可能不同，BPS 并非固定数量候选框的单次延迟。

### 2.3 可变长度不等于一次生成所有对象

轨迹请求可以声明路点数量；密集运动以一帧未来查询点作为一块；检测中每块可以对应一个框，再继续生成其他对象。单个框内部并行与整幅图所有目标同时产生，是不同的并行层级。

驾驶任务也有不同输出协议：项目页举出的 NAVSIM 为四秒八点，Waymo 为五秒二十点，Alpamayo 为 6.4 秒六十四点。需要分别核对坐标系、时间间隔和输出维度。

## 3. 视觉计划怎样影响动作 {#control}

VFlash 输出的计划并非直接发给电机。下游动作模型通过交叉注意力读取冻结 VLM 的计划特征，再生成控制动作。

MolmoSpaces 使用由 Cosmos-Predict2.5 后训练得到的世界动作模型。它保留图像与机器人状态输入，同时读取问题、子任务和轨迹特征；输出二十步动作块，每三个块重新规划。

LIBERO 路线则使用 PIv3 扩散动作头，结合主相机和腕部相机图像，在八动作块之前预测子任务与十路点的二维加三维轨迹。两条路线的动作块和重规划频率不能混用。

动作头需要针对控制任务训练，冻结 VLM 不等于整个系统无需训练。空间预测更准确也不是成功率必然提高的充分条件：动作头是否学会使用计划、观测是否有效、环境是否与训练一致，都会影响执行。

## 4. 如何阅读精度与速度结果 {#results}

### 4.1 位移误差和任务成功率分别统计

轨迹常用平均位移误差 ADE 与终点误差 FDE。对相同时间对应的 N 个预测点，ADE 是各点欧氏距离的均值，FDE 是最后一点的距离。只有对齐坐标系、单位、有效点掩码和时间戳，指标才可比较。

项目页报告，三个机器人数据集、三种目标变体的平均三维 ADE 相比 AR 下降 42.6%。首页的最高降幅是某项设置的结果，不能写成所有任务均降低相同比例；二维和三维误差也不能直接相加。

MolmoSpaces 的等权四套件平均成功率如下：

| 配置 | 平均成功率 |
| --- | ---: |
| 原始基线 | 62.6% |
| AR 二维加三维计划 | 61.0% |
| 保留子任务、以图像特征替代轨迹特征 | 63.7% |
| VFlash 三维计划 | 69.3% |
| VFlash 二维加三维计划 | 70.2% |

这些消融使用相同 WAM 架构和训练预算，但上下文特征不同。AR 计划低于原始基线，提醒我们“增加计划”并不自动有益；移除几何后收益缩小，则支持几何信息确实参与了控制。

### 4.2 解码提速与模型流水线提速

项目页 Thor 示例中，AR 解码从 3107.6 ms 降到 258.2 ms，约为十二倍；模型阶段总耗时从 3552.7 ms 降到 703.3 ms，约为 5.1 倍。

用这个数值检查串行瓶颈：AR 的非解码部分约为 445.1 ms。即使把解码变成零，这部分也依然存在。因此，十二倍局部加速不能直接当作十二倍控制吞吐。

计时使用 batch size 1、同一时间一个请求和 CUDA events。总数包括已测量的视觉、预填充、解码和动作模型阶段；不包含模型加载、引擎构建、预热、文件加载、被排除的 CPU 预处理和输出反分词。它不是从传感器曝光到执行器完成的闭环延迟。

### 4.3 运行时设置也是比较条件

官方速度使用定制 TensorRT-Edge-LLM 与 TensorRT 引擎，覆盖 Thor、Spark 和 H100。视觉、目标、草拟引擎及 KV 缓存采用 FP16，没有把权重或 KV 量化收益混入该比较。动作模型使用另外配置的精度和注意力实现。

驾驶质量评估使用五次 DDIM，而延迟比较使用十次以匹配对照规划器。复现时需要同时记录动作头步数，不能把不同步数的质量和耗时拼成同一个设置。

## 5. Eagle/Embodied 实际提供什么 {#code}

本文固定 Eagle 提交 `783f656d127ee498137b5ff52603ce36c292d317`。该目录 README 的标题是 LocateAnything，核心是 Parallel Box Decoding（PBD）：将框或点作为原子单位并行预测。

| 项目 | VFlash 项目页 | Eagle/Embodied 当前发布 |
| --- | --- | --- |
| 主要任务 | 视觉计划及其下游控制 | 通用视觉定位与检测 |
| 几何单位 | 框、轨迹、密集运动等 | 框和点 |
| 模型关系 | 冻结目标 VLM，训练轻量 drafter | LocateAnything 模型与其混合解码实现 |
| 输出消费者 | 世界动作模型或扩散动作头 | 检测、定位与评估接口 |
{.table-readable}

二者共享利用几何结构组织并行解码的思路，但训练对象、覆盖任务和运行时并非同一套发布接口。LocateAnything 的框格式回退逻辑，不能直接当作 VFlash 轨迹必须逐 token 验证的依据。

### 5.1 可用 Worker 接口与输出

README 展示 `LocateAnythingWorker`，提供 detect、ground_multi、detect_text、ground_gui、point 等入口。用户输入图像和语言查询，返回定位答案，而不是机器人关节轨迹。

框输出使用四个 0–1000 的归一化坐标。若原图宽 W、高 H，横坐标乘 W/1000，纵坐标乘 H/1000。例如 640×480 图像中的框坐标 250、250、750、750，对应像素框 160、120、480、360。

解析后仍要检查上下界和边的顺序，并确认预处理是否裁剪、缩放或补边。二维像素框还不能直接变成三维抓取位姿：需要深度、相机标定、外参、抓取生成和运动约束。

### 5.2 混合解码与后端条件

LocateAnything 默认采用快速 MTP 路径，遇到格式异常或空间歧义时回退到已验证前缀，再用 NTP 重解问题块。它的失败恢复机制属于这套定位模型，读源码时应分别追踪状态、缓存和输出边界。

README 的可选 `la_flash` 批处理运行时发布在 Hugging Face 模型仓库中，不应假设 GitHub 目录本身已经包含全部文件。其 FlashAttention 稀疏范围路径面向推理与评估；训练仍采用标准模型路径。MagiAttention 的硬件条件也与该替代推理后端不同。

官方 A100 的单次 4K 输入探测中，稀疏路径主要减少保留显存，耗时只从约 8.26 s 变为 8.03 s。这不是 VFlash 的五倍机器人推理结果，也不能用峰值保留显存替代模型参数占用或常驻显存。

### 5.3 训练与发布能力不能混同

Embodied 提供持续 SFT 与视觉提示微调说明，以及 LoRA 配置。这里训练的是 LocateAnything；不能把其 block_size、冻结范围或学习率照搬成 VFlash drafter 的论文配置。

README 明确说明，公开 LocateAnything-3B 权重尚不直接支持视觉提示推理，尽管训练代码已经支持视觉提示微调。代码能力、权重能力和运行时依赖需要分别确认。代码与模型也有不同许可，应分别阅读仓库 LICENSE 与模型许可。

## 6. 接入系统时的检查顺序 {#integration}

先确定任务需要定位结果、视觉轨迹还是控制动作，再选对应发布物。只有框检测需求时，Worker 接口更直接；若要重建 VFlash 控制链路，还要找到匹配目标 VLM、drafter、动作头和定制运行时，不能仅靠 Embodied 安装成功来判断完成复现。

其次固定几何协议：坐标系、单位、归一化范围、时间间隔、相机到机器人变换以及有效点数量。格式正确的三维轨迹仍可能越界、碰撞或超过速度限制。

最后分别记录视觉误差、任务成功率和阶段延迟。缓存回填与下游特征提取应进入预算；传感器更新、通信、控制器跟踪和动作块执行需要在系统级另行测量。VFlash 提升的是视觉规划生成与使用效率，真实机器人执行仍依赖完整的感知—规划—控制契约。

<details>
<summary>参考答案与解析（9 项，顺序对应上文）</summary>

1. 边界确定一块输出哪个完整对象，位置确定每个槽代表哪一轴或分隔符。只对齐块边界仍可能因数字 token 宽度变化而把后续坐标错位。

2. 几何 drafter 直接学习标注几何，质量按空间误差等评价；它不要求逐 token 复制 AR 输出，也不保持普通文本推测解码的完全相同分布保证。

3. 冻结只是不更新参数，生成基元仍要送回目标 VLM 更新缓存、提取计划特征，因此存在前向与数据传递成本。

4. 视觉计划是框、点或路点；下游动作头结合观测与计划特征生成控制命令，还需坐标转换和执行约束，不能直接发给电机。

5. Thor 示例解码约 3107.6/258.2≈12.0 倍，总模型阶段约 3552.7/703.3≈5.1 倍；视觉、预填充和动作模型等成本仍在，传感器到执行器延迟另计。

6. 固定 Eagle/Embodied 发布的是 LocateAnything 的框/点定位与混合解码，共享几何并行思路，但不是完整 VFlash drafter、控制动作头与运行时的同一发布。

7. 0–1000 坐标的横轴乘原宽/1000，纵轴乘原高/1000。640×480 上 (250,250,750,750) 映成 (160,120,480,360)，还需核对裁剪/补边协议。

8. 训练代码支持一种输入，只证明训练路径存在；公开 checkpoint 未必已训练这种能力。本文固定版本说明 LocateAnything-3B 尚不直接支持视觉提示推理。

9. 结构校验及框的空间置信度保护通过后直接接受；失败时用受约束 AR 重生成。轨迹不保留草稿前缀，框可保留首个不确定坐标前部分；格式通过仍不证明物理可执行。

</details>
