## 字节流与数据报

TCP 提供可靠有序的字节流，应用仍需定义消息边界。UDP 保留数据报边界，但不保证送达、顺序或去重。选择协议前，先说明业务需要的是完整历史、最新状态，还是必须确认执行结果的一次操作。

| 维度 | TCP | UDP |
| --- | --- | --- |
| 接收单位 | 一段字节流，可能短读 | 一份数据报，缓冲区不足会截断 |
| 连接语义 | 建立传输连接 | 无 TCP 式握手，connect 可设置默认对端 |
| 应用责任 | 分帧、超时、业务确认与重连 | 长度限制、丢包处理、去重与拥塞策略 |
| 不能默认获得 | 身份认证、加密、业务幂等 | 可靠性、保序、机密性 |

这些是传输语义，不是应用性能排名。TCP 可能因重传等待后续字节，UDP 应用也可能自行重传、排队并产生高延迟。[TCP 标准](https://www.rfc-editor.org/rfc/rfc9293.html)与 [UDP 应用指南](https://www.rfc-editor.org/rfc/rfc8085.html)分别说明了传输服务和上层设计责任。

## 一次发送为什么不是一条接收消息

假设应用发送两个消息体 `HELLO` 和 `OK`，每个消息前加 4 字节大端长度：

```text
应用消息： [00 00 00 05 | H E L L O] [00 00 00 02 | O K]
接收方式 A：[00 00] [00 05 H E L] [L O 00 00 00 02 O K]
接收方式 B：[00 00 00 05 H E L L O 00 00 00 02 O K]
```

两种接收方式都合法。TCP 负责顺序和传输完整性，应用负责积累 4 字节头、检查长度上限，再积累对应数量的消息体。不要将缓冲区末尾补零后的 C 字符串长度当作实际收到的字节数；消息中可能包含零字节，UTF-8 字符也可能跨接收边界。

下面只验证分帧逻辑，不创建 socket。`chunks` 模拟多次读取到的字节片段，流结束时仍剩半条消息会报错。

```python
def decode_chunks(chunks, max_length=1024):
    buffer = bytearray()
    messages = []
    for chunk in chunks:
        buffer.extend(chunk)
        while len(buffer) >= 4:
            length = int.from_bytes(buffer[:4], "big")
            if length > max_length:
                raise ValueError("message exceeds the configured limit")
            if len(buffer) < 4 + length:
                break
            messages.append(bytes(buffer[4:4 + length]))
            del buffer[:4 + length]
    if buffer:
        raise ValueError("stream ended in the middle of a message")
    return messages


expected = [b"HELLO", "机械臂".encode("utf-8"), b""]
wire = b"".join(len(body).to_bytes(4, "big") + body for body in expected)
assert decode_chunks([wire]) == expected
assert decode_chunks([wire[i:i + 1] for i in range(len(wire))]) == expected
for cut in range(len(wire) + 1):
    assert decode_chunks([wire[:cut], wire[cut:]]) == expected
print("all byte splits preserve the same three messages")
```

这是有限输入的解析实验。真实服务还要限制读取缓存、连接数、整条消息的完成期限和输出队列，不能因为单个消息不超过上限，就允许无限数量的消息同时驻留内存。可继续使用本站的 [C++ TCP 完整示例]({{< relref "/posts/network-protocol/c++_tcp" >}})练习短读、短写和长度前缀。

## UDP 的边界、截断与零长度报文

一次 UDP 接收对应一份数据报。若接收缓冲区太小，在本文 Linux socket 场景中，超出的内容会被丢弃；下一次接收不会自动拿到上一份报文的剩余部分。因此应明确最大业务报文长度，并通过接口提供的截断标志拒绝不完整消息。

UDP 零长度数据报可以是合法消息，不能照搬 TCP 中请求读取正长度时 `recv` 返回 0 表示对端有序关闭的解释。对 UDP 调用 `connect` 也不会变成 TCP：它主要指定默认对端和接收来源，不能证明另一端程序已经启动。

大报文还可能导致 IP 分片，任一分片丢失就会影响整个数据报。实际业务通常应控制报文尺寸并遵循路径 MTU 与拥塞控制要求，不能把协议字段的理论上限当作推荐业务包长。Linux 的截断和超时处理可见 [C++ UDP 示例]({{< relref "/posts/network-protocol/c++_udp" >}})。

## 机器人消息需要表达什么

以下是应用协议设计项，不是 TCP 或 UDP 自带的机器人语义：

| 信息 | 要解决的问题 | 常见错误 |
| --- | --- | --- |
| 消息类型与协议版本 | 同一端口区分状态、请求与结果 | 将不同版本的结构体按原布局解析 |
| 长度与字段编码 | 明确帧边界、字节序和字符串编码 | 直接发送含填充字节的内存结构体 |
| 会话与序号 | 检测重复、乱序和重启后的新序列 | 发送端重启后把新消息长期当作旧包 |
| 观测时间与有效期 | 判断数据是否仍适合当前决策 | 队列里的旧指令迟到后继续执行 |
| 坐标系与单位 | 明确米、毫米、角度与参考系 | 相同维度的数组被误当成同一语义 |
| 请求 ID 与执行状态 | 关联重试、接受、开始、完成和失败 | 收到报文就回复“动作完成” |

跨机器时间戳只有在时钟关系已知时才能直接相减。如果没有同步，先用接收端单调时钟测量本地排队时间，用请求—响应测 RTT；不要把两个任意时钟的差值当作单向网络延迟。

### “已经发送”“已经接收”和“已经完成”是三个事件

`send` 成功通常表示数据被本机协议栈接受。TCP 的传输确认也不是机器人动作完成的确认。一个业务请求可以先返回“已接受”，稍后才报告“已完成”或“失败”，调用方需要分别设置期限。

重连后重发“设置目标位置”与重发“向前再移动 10 cm”的含义也不同。后者重复执行可能累积位移，应使用请求 ID 和明确的去重/恢复规则。即使传输层是 TCP，连接中断发生在动作执行之后、结果返回之前，调用方仍可能不知道业务是否已完成。

### 最新状态与完整历史使用不同队列策略

相机姿态、摇杆设定等连续状态，过期样本可能应该被新样本替换；日志文件则需要保留完整顺序。是否丢弃旧数据由应用语义决定，不能仅靠选择 UDP 来解决。

例如 50 Hz 的状态流每 20 ms 产生一帧，若处理速度更慢而队列持续增长，最新收到的数据也可能来自很久以前。应同时记录产生时间、接收时间、处理时间和队列深度，区分网络延迟与应用积压。

## 从本机实验开始

先在 `127.0.0.1` 测试单次请求—响应，确认发送长度、接收长度和退出码，再考虑局域网地址、防火墙和网络故障。不要把广播作为默认示例，也不把应用调试端口直接暴露到公网。

测试至少包括对端不存在、提前退出、错误长度、超时、零长度消息与多次重复请求。机器人通信还需独立的状态机、指令有效期与硬件安全措施，传输协议本身不能代替这些保障。

| 测试 | 应能区分的结果 |
| --- | --- |
| 每次只送一个字节 | TCP 解析器仍恢复同一消息序列 |
| 一次送多条消息 | 不能误合并为一个业务请求 |
| 长度字段超过上限 | 在分配大消息缓存前拒绝 |
| 消息体未收完就断开 | 报告截断，不能当作正常完整消息 |
| UDP 报文大于接收缓冲区 | 报告截断，不能解析残缺字段 |
| 重复或乱序请求 | 按应用约定去重、丢弃或重排 |
| 处理暂停后恢复 | 根据有效期处理积压，不能盲目追赶旧指令 |

- 给聊天、遥测和文件传输分别列出时延、可靠性及顺序需求，再解释为什么选择某种传输或应用协议。
- 写出应用消息的边界和最大长度；即便使用 TCP，也仍需要定义消息格式与失败处理。
