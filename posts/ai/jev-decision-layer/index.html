Jev 可以承担“当前该选哪个动作”的判断，但机器人能看见什么、允许执行什么、怎样执行，仍由整个系统共同决定。 它不是 RT-2、OpenVLA 或 π0 那样的视觉—语言—动作模型；更准确的定位，是可嵌入分层智能体的类型化决策服务。

以关抽屉为例：上层给出局部目标，感知模块报告把手与接触状态，程序列出可用技能，Jev 返回其中一个 ID。执行器检查这个选择是否仍然有效，再调用相应技能；下一轮依据实际观测继续选择或交回上层。本文将沿着这条链路，逐项说明每个模块需要什么信息、承担什么判断。

本文核对资料的日期为 2026-09-29。先介绍公开接口，再读 Jev-Mobile 的 GUI 实验与社区机械臂仿真，最后给出机器人集成设计。文中的机械臂候选、门控代码和消融方案是独立示例，不是已部署的 Jev 机器人产品。

1. Jev 是什么：把语义判断变成可调用的类型

TypeSafe 将 Jev 定义为 System One 模型：输入状态与类型化问题，输出程序可以消费的结构化判断。这里的 “System One” 是产品与架构定位，重点是供程序使用的有限选择、等级和二元判断。公开入口介绍了接口和使用方式；本文没有找到足以复现其完整网络、权重与训练配方的公开材料。官方介绍

因此，“轻量”应先理解为交互接口短、决策成本较低的设计目标，不能擅自换算成几亿参数、本地 CPU 推理或开源小模型。当前文中讨论的是通过服务调用的 Jev；部署位置与选择范围要分开讨论。

本文所核对的版本是 jev-1.13.0。官方模型页明确列出纯文本输入，支持字符串、JSON 对象或文本数组；图像、音频与视频需要先由上游转换。jev-latest 等别名会随发布改变，复现实验应同时固定请求版本并保存响应中的实际模型 ID。模型页还区分整次请求与“状态加最长问题”的上下文预算，不能仅检查单个 state 字段的长度。模型版本与输入限制

1.1 三种输出并不等价

类型输入定义输出含义机器人中的示例问题
Choice一个有限选项集合选择项、各项概率与 confidence下一步选择重新观察、接近把手还是重规划？
Score按顺序排列的等级描述等级分布、加权分数与 confidence当前进展属于无进展、部分推进还是目标达成？
Noul一个二元语义命题命题为真的概率估计，没有单独的 confidence 字段当前描述是否支持“物体已经抓稳”？

接口细节分别见 Choice、Score 与 Noul。这三类都没有直接定义末端位姿、关节扭矩或一段运动轨迹。

例如，把 Score 的三个等级设为“没有进展”“有进展但未完成”“目标完成”，若分布是 (0.1,0.6,0.3)(0.1,0.6,0.3)(0.1,0.6,0.3)，按等级下标计算的分数是：

0×0.1+1×0.6+2×0.3=1.2. 0\times0.1+1\times0.6+2\times0.3=1.2. 0×0.1+1×0.6+2×0.3=1.2.

这个数是等级位置，不是完成了 60%，不是前进了 1.2 米，也不是成功率 1.2。即使两个状态都有分数 1，(0,1,0)(0,1,0)(0,1,0) 与 (0.5,0,0.5)(0.5,0,0.5)(0.5,0,0.5) 所表示的不确定性也完全不同。将语言等级变成连续控制量，需要另行定义物理意义，不能直接乘一个速度系数。

1.2 “结构正确”与“判断正确”是两件事

有限候选给程序提供明确的 ID 白名单，可以据此拒绝不存在的技能名，却不能保证选中的技能适合当前世界。设候选只有“向左”和“向右”，模型可以非常确信地选左；但真正需要的可能是“松开后重新抓取”。输出仍然符合类型，任务仍然失败。

还要区分不返回自由文本解释与没有任何返回数据或输出 token 统计。API 仍返回 JSON 与用量信息；不能仅因接口不返回一段文字理由，就断言网络传输、用量记录或序列化开销为零。

1.3 RLCD 公开了什么，还没有公开什么

TypeSafe 把其训练方向称为 Reinforcement Learning for Calibrated Decisions，RLCD：希望输出既能用于决策，也能表达可用的不确定性。其公开说明强调概率校准；目前这里核对的材料没有给出足以复现训练的完整数据、奖励公式、优化器和权重。官方训练定位

读到 RLCD 时，可以确认“训练目标重视类型化判断与概率”，却不能自行补成某个 PPO／GRPO 配方，也不能把后文的 Brier score 推导当作 Jev 已公开采用的损失函数。接口表现、模型内部结构、训练目标与特定 benchmark 的结果，是四种不同层次的证据。

按当前模型页，服务不提供使用客户数据进行微调或 LoRA 适配；领域规则主要通过状态、问题要求和选项描述传入。因此，接入一个新技能库时，需要验证的是状态表达、候选语义与路由阈值，而不是假设上传若干机器人轨迹就能得到专属 Jev 权重。领域适配方式

路线决策规则从哪里来适合检查的问题
确定性规则程序员明确编写条件条件已能精确计算时，是否还有调用模型的必要？
固定类别分类器带标签数据与分类训练类别、数据分布和标签成本是否稳定？
生成模型的结构化输出语言模型加受约束的输出接口在同一候选与预算下，准确率、延迟和校准如何？
Jev 类型化判断通用决策服务，输入包含问题与选项语义动态候选是否被理解，概率能否支撑本项目的路由？

这张表按接口与验证任务分类，不是模型优劣排名。尤其当程序已经算出“目标在左侧、右侧有障碍”，而唯一规则就是向左时，换成模型并不会自动增加系统能力。更值得测试的是需要结合语言目标、状态语义与多个可行技能的选择。

2. 放进机器人系统：规划、选择与控制各做什么

一种合理的集成方式，是让上层把“整理桌面”拆成局部目标，让中间层在当前允许的技能里选择，让底层完成轨迹跟踪。Jev 可承担中间的语义选择，但它并不要求所有 VLA 都必须改成这一架构。

层次典型输入与输出主要责任
感知与状态估计图像、深度、本体反馈 → 对象、关系、状态与不确定性让决策依据对应真实观测
高层规划总任务、当前状态、历史 → 局部目标分解任务、处理新情况与失败恢复
候选构造与选择局部目标、当前状态 → 有界技能 ID程序定义选项，Jev 或其他选择器做语义判断
技能与运动控制技能参数 → 轨迹与控制量接触、跟踪、约束和执行反馈
独立运行保护传感器、控制状态 → 限制、停止或许可不以模型自报置信度代替实际约束检查

这里的“独立运行保护”是机器人集成所需的职责划分，不是声称本文的几行 Python 已实现安全控制器。真实系统仍需自己的限位、速度与力约束、急停及故障响应。

2.1 不能把全部 VLA 描述成“每个伺服周期都调用大模型”

动作块模型已经可以一次预测多个未来控制点，然后逐步执行。π0 的流匹配采样迭代、动作块更新与机器人执行频率是三个不同概念；详见 VLA 演进中的 Flow Matching。因此，Jev 的比较对象应是具体调用方式下的逐步生成式决策器，而不是抽象地宣称所有 VLA 都必须逐周期生成文字。

2.2 “2–14 Hz”只是特定延迟的倒数

TypeSafe 发布文章报告的端到端服务延迟范围是约 70–500 ms，并带有测试地点等条件。这属于提供方报告，不是机器人控制周期保证；后文的社区记录也展示了不同运行条件下更长的网络调用延迟。发布文章

仅把它取倒数，可得：

10.5=2,10.07≈14.3. \frac{1}{0.5}=2,\qquad \frac{1}{0.07}\approx14.3. 0.51​=2,0.071​≈14.3.

但串行闭环每轮还要经历：

Tloop=Tobserve+Tbuild+Trequest+Tgate+Texecute. T_{\mathrm{loop}}=T_{\mathrm{observe}}+T_{\mathrm{build}} +T_{\mathrm{request}}+T_{\mathrm{gate}}+T_{\mathrm{execute}}. Tloop​=Tobserve​+Tbuild​+Trequest​+Tgate​+Texecute​.

这里 request 已包含相应服务调用与网络等待，不应再次重复加同一段网络时间。假设观测与候选构造 40 ms，请求 150 ms，门控 2 ms，动作与稳定等待 300 ms，那么一轮 492 ms，约 2.03 Hz；这组数仅用于解释预算。并发可以提高吞吐，但尚未观察动作结果的请求，不能算作同一个因果闭环的下一步。

2.3 感知成本不会因为换了选择器而消失

如果每一帧仍需调用一个 VLM，才能把图像转写成 Jev 可用的状态，那么系统虽然减少了“生成动作文字”的工作，仍承担逐步视觉理解的费用和等待。相反，若对象跟踪、深度几何与本体反馈已能稳定给出所需字段，低频 VLM 才更容易集中于目标解释和异常恢复。

因此应沿完整链路记账：图像如何变成状态、状态何时生成、是否缓存、缓存何时失效、选择器调用后还要等待哪些动作。Jev-Mobile 使用已有无障碍树构造文字候选，是一种特定的结构化观测条件；机械臂未必天然具备同等完备的对象与接触状态。把 GUI 的费用变化迁移到机器人，必须重新计算这部分输入成本。

3. 一条动作究竟是什么

“打开抽屉”在不同系统里可能完全不同：对任务规划器是一个子任务；对技能库是一次带参数调用；对接触控制器则包含接近、抓取、拉动和释放。设计 Jev 接口前，应先写清粒度。

候选形式选择器实际承担什么仍由其他模块承担什么
GUI 的点击、滚动、输入在屏幕关联的选项中做选择定位元素、输入文本与设备执行
“抓取把手”这样的技能选技能与目标对象抓取位姿、轨迹、接触与终止条件
XYZ 方向与夹爪离散选项在量化动作空间中选局部方向步长、坐标系、碰撞与动力学
VLA 生成的多个动作块对已有候选进行选择或排序产生候选、预测后果与跟踪执行

最后一种是可研究的设计，不是本文已经找到的 Jev 官方功能。它还引入额外问题：若原始动作块都不合适，重排序没有办法凭空生成好动作；若用单帧描述给未来动作块评分，也未必具有足够的时序信息。

从连续空间离散化为候选，还会产生分辨率取舍。步长大，调用次数少但接触更粗糙；步长小，选择更精细但反馈链路更长。把一个轴拆成多个 Choice 也不能免除组合约束：分别允许的 X、Y、Z 增量，合成后可能超出速度上限或进入障碍物。

例如，程序规定一次平移增量的总幅值不超过 10 mm，X、Y 两个通道各选 8 mm，合成幅值却是 82+82≈11.3\sqrt{8^2+8^2}\approx11.382+82​≈11.3 mm。两个单轴值分别通过检查，不能证明组合通过。坐标系也应留在候选参数中：相机画面的“左”与机器人基坐标的负 X 不一定相同，变换与单位换算应由程序完成。

4. Jev-Mobile：从论文里逐步还原闭环

Jev-Mobile 预印本研究 Android GUI 操作，作者是 Linghua Zhang，2026 年 9 月发布。它是理解“VLM 规划 + 类型化执行”的直接材料，但其结果不能直接当作机械臂 benchmark。

4.1 上层看什么，下层看什么

VLM 读取任务、当前截图、无障碍树及程序记录的真实操作历史，输出局部目标与必要的精确输入文本。程序根据当前原始无障碍树枚举动作。Jev 读取树的文字表示、局部目标、本轮委派历史和候选描述，选一个 ID，或返回 DONE / BLOCKED。

该版本保留原始树的文字表示，没有先训练一个语义图压缩器；长树与噪声也会进入决策输入。交接时，上层使用当前截图、当前树以及按局部目标分组的动作记录，系统不再追加一轮生成式“执行总结”。历史超过字符预算时，程序按约定压缩旧组并记录省略情况；这也意味着接口预算会影响上层能回看多少执行细节。

每执行一个原子动作，系统重新观测、重建候选，再继续选择。这里的“局部执行”指决策范围；论文中的 Jev 是远程服务，不能把 local executor 翻译成“手机端本地推理”。论文也没有把评估器隐藏的任务答案交给选择器。

该方法没有为这套 AndroidWorld 实验增加新的模型训练，也没有训练一个交接路由器；局部目标、候选构造和动作历史共同形成执行协议。理解这项工作时，应先还原协议如何减少逐步规划调用，再讨论换用其他选择模型的结果。方法与实现边界

一次委派可能是：

  1. VLM 指定“找到通知开关并关闭”，而不是预写所有屏幕坐标。
  2. 当前树提供“设置列表”“向下滚动”等候选，Jev 选择滚动。
  3. 新页面出现“通知”元素；程序重新分配本轮有效 ID，Jev 再选择进入。
  4. 观察到开关状态满足局部目标，Jev 返回 DONE。
  5. 上层根据真实执行历史判断整个任务是否结束，或继续下一局部目标。

这是用于说明协议的例子，不是引用论文中的某一条原始轨迹。关键是第 3 步：旧页面的 ID 和坐标不能直接沿用到新页面。

4.2 DONE 与 BLOCKED 为什么必须存在

控制器把 DONE、BLOCKED 与当前动作 ID 一起写入 Choice 的 criteria，并说明各自含义。它们是这套协议定义的交接选项；后文离线脚本用小写 done、blocked 作为自己的候选 ID。论文的类型化决策定义

DONE 表示局部委派应该结束，不等于 AndroidWorld 判定整个任务成功。BLOCKED 表示当前选项或信息不足，需要把控制权交回上层。两者避免选择器在所有候选都不合适时，仍被迫选一个动作。

论文第一版直接使用原始树构造候选，没有依靠额外视觉坐标补全来修复树中缺失的目标；精确输入值由规划器提供，输入还受可打印 ASCII 等实现限制。这些限制会影响候选覆盖，不能全部归因于 Jev “不够聪明”。方法细节与约束见论文第 3 节。

6.2 把失败拆成覆盖、选择与交接

评测前要区分普通技能、补充观测和控制权交接。若衡量普通技能的候选覆盖，只对需要选择这类技能的状态计数；不能因为总有 BLOCKED 可选，就把技能缺失也记成已覆盖。

对这 NNN 个状态，令 At⋆A_t^\starAt⋆​ 为标注规则下可接受的普通技能集合，则候选覆盖可以记为：

Coverage=1N∑t1[Ct∩At⋆≠∅]. \mathrm{Coverage}=\frac{1}{N}\sum_t \mathbf 1[C_t\cap A_t^\star\ne\varnothing]. Coverage=N1​t∑​1[Ct​∩At⋆​=∅].

在“一步必须从当前候选选出可接受动作”的评测里，整体正确率等于覆盖率乘以覆盖条件下的选择正确率。候选只有 80% 的状态覆盖时，选择器即使在有解状态上达到 100%，这项整体一步正确率也最多 80%。这不是整段任务成功率上界：多步系统可能通过重新观察和重规划恢复。

交接还应单独统计：提前 DONE、应该 BLOCKED 却继续动作、目标完成后仍重复执行。记录事件原因与观测版本，比只存最终 ID 更有助于复盘。

6.3 状态压缩也可能把问题变成无解

想象两个场景：A 中红杯在左、蓝杯在右；B 中位置互换。目标都是“取红杯”，候选都是“取左杯”或“取右杯”。若上游只输出“两只杯子可见”，那么两种场景传给 Jev 的状态、问题与选项完全相同。

如果每次独立、等概率出现这两种场景，并且必须立即二选一，任何只读这份状态的选择器都面临相同限制。令它选择左杯的概率为 qqq，则平均正确率为：

Pr⁡(correct)=12q+12(1−q)=12. \Pr(\mathrm{correct})=\tfrac12q+\tfrac12(1-q)=\tfrac12. Pr(correct)=21​q+21​(1−q)=21​.

这里的 50% 是限定信息与动作空间下的算例，不是 Jev 实测结果。一旦允许读取颜色位置、请求新观测或交回 VLM，输入条件改变，这个上界便不再适用。

因此，一份可用状态应按决策需要保留：对象身份和关系、坐标系和单位、接触与可见性、最近动作的实际效果，以及哪些字段未知。unknown、未观测和已确认的 false 应分开；“没看到抓稳”不能自动写成“确认没有抓稳”。数字转换、计数和几何比较放在代码中，语义字段仍应保留可追溯的观测依据。

6.4 观测年龄与请求延迟是两个时钟

设观测采集时间为 tot_oto​，请求发出时间为 tst_sts​，响应到达时间为 trt_rtr​，准备执行时为 tet_ete​。同一时间基准下：

ObservationAge=te−to,RequestAge=te−ts. \mathrm{ObservationAge}=t_e-t_o,\qquad \mathrm{RequestAge}=t_e-t_s. ObservationAge=te​−to​,RequestAge=te​−ts​.

请求年龄只从发出请求开始计时，不能覆盖此前的感知预处理、排队与候选构造。服务调用的往返耗时则是 tr−tst_r-t_str​−ts​；若响应到达后又排队，执行时的请求年龄还要加上 te−trt_e-t_rte​−tr​。不要把这两个量混成同一个“模型延迟”。

假设观测在 9.0 秒采集，请求在 10.125 秒发出，10.25 秒收到响应并立即准备执行：请求只经历 0.125 秒，但观测已经旧了 1.25 秒。若门控误用请求时间当作采集时间，就会把旧观测判断为新鲜。脚本分别保存观测年龄与请求年龄，并在实际准备提交时重新计算。

6.5 结果返回后，还差一次提交与一次结果确认

假设一个动作已经提交，设备完成了点击或移动，但确认消息丢失。此时“没有收到成功返回”并不意味着“动作没有发生”。再次发送同一动作可能导致重复输入、额外位移或错误的状态切换。先查询实际状态，再决定补发、恢复或交接，才能将网络结果与物理结果分开。

相对地，重新请求一次 Jev 判断通常只产生新的推理费用与等待，并不会自行移动机器人；但第二次响应仍可能基于过期状态。SDK 支持重试和退避，具体预算应与本轮决策的截止时间对齐，不能把一般服务调用的重试设置直接当作控制周期。SDK 重试说明

一次可复盘的事件记录可以依次保存“请求已发出 → 响应已验证 → 动作已提交 → 结果已观测”。其中被拒绝的响应也要记原因，但不能混入“实际执行动作”的历史。Jev-Mobile 的论文采用实际动作历史交接，并明确指出非幂等动作的确认不明时先检查。论文的观测绑定与历史约定

7.1 概率分布并不是物理成功保证

Choice 给出的概率是针对本次问题与候选集合的相对判断。它不自动等于抓取成功率、无碰撞概率或任务最终完成率。缺少“以上皆不合适”时，所有选项都很差也仍需在它们之间分配概率。

7.2 一次返回多个问题，不等于得到联合动作分布

若分别询问 X、Y、Z 方向，每题是针对同一输入独立求值的接口问题；这些边缘答案不保证逻辑一致，也不能未经假设就把概率相乘，声称获得整个运动的成功概率。需要互斥时，可以把允许的组合定义成一个 Choice，或由程序投影到合法动作集合；后者改变了实际动作，应记录变换并重新检查有效性。

7.3 置信门控应与观测门控串起来

一种可检验的处理顺序是：

  1. 检查时钟与活动目标；目标已变更时，旧响应交回规划处理。
  2. 观测过期或快照不匹配时重新观测；请求超过有效期时，记录过期并进入恢复路径。

7.6 校准、区分能力与成本还要分别检查

若某个输出 qiq_iqi​ 被明确设计成二元事件 YiY_iYi​ 的概率，才有理由问：“预测接近 0.9 的那组事件是否约有 90% 发生？”这与“分布很集中”不同。常用的二元 Brier score 为：

Brier=1N∑i(qi−yi)2. \mathrm{Brier}=\frac1N\sum_i(q_i-y_i)^2. Brier=N1​i∑​(qi​−yi​)2.

9.1 离线回放能隔离判断，闭环评估才能观察后果

离线比较时，把同一份观测、局部目标与候选快照交给不同选择器，检查它们选了什么。这样容易隔离模型判断，也能针对遮挡、缺项和过期响应构造反例。但记录中的下一帧来自原来执行过的动作，不一定是新选择器采取另一个动作后会到达的状态。不能把“换个 ID 后继续播放原视频”当作新的真实闭环轨迹。

闭环比较则从配对初态分别运行，各系统执行不同动作后，可以到达不同状态。此时最终成功率、恢复次数与任务费用都有意义，但结果同时包含状态分布变化。两类实验互相补充：先用固定状态定位候选或选择问题，再用闭环判断改进是否真的帮助任务。

可以增加三项接口扰动：保持物理意义不变，只交换候选顺序、重新命名不含语义的 ID，或用等价句改写选项。若输出对这些变化非常敏感，说明接口表述影响很大。每次必须保留 ID 到实际技能的映射，不能把一次重命名误算成选择了另一个物理动作。

9.2 任务、轨迹与单步记录应有不同统计单位

一个长任务产生很多相邻步骤，不等于获得同样数量的独立任务样本。建议同时保存任务级完成结果与步骤级选择记录，明确分母；划分数据时优先按完整轨迹或环境分组。同初态配对比较，还应保留哪一对任务两者都成功、只有一方成功或两者都失败，而不只报告总体均值。

单步正确率也不能直接换算成长任务成功率。作一个独立算例：任务固定 20 步，只有全部选对才成功，任一步错误都不可恢复。若各步相互独立且正确率均为 95%，成功概率是 0.9520≈35.8%0.95^{20}\approx35.8\%0.9520≈35.8%；若每个任务要么全部选对、要么全部选错，并有 95% 的任务全部选对，则各步正确率仍是 95%，任务成功率却是 95%。两组相同的单步数字，对应不同的错误相关性。真实机器人还可能恢复，因此应测完整闭环，不能直接套这两个算例。

延迟至少区分一次请求、一次完整决策、一次技能和整个任务。重试等待应进入实际经历的请求或决策延迟；超时按单独的失败/删失记录保留，不要丢掉以后再计算一个更漂亮的 p95。尾延迟的估计同样依赖样本数，十几次调用无法支持精确稳定的高分位结论。

9.3 费用按尝试记账，再按问题汇总

成本也建议同时保留两种量：

成功轨迹条件均价=∑i:yi=1Ci∑iyi,全部尝试的每成功成本=∑iCi∑iyi. \text{成功轨迹条件均价}= \frac{\sum_{i:y_i=1}C_i}{\sum_i y_i},\qquad \text{全部尝试的每成功成本}= \frac{\sum_i C_i}{\sum_i y_i}. 成功轨迹条件均价=∑i​yi​∑i:yi​=1​Ci​​,全部尝试的每成功成本=∑i​yi​∑i​Ci​​.

这里 yiy_iyi​ 表示整次任务是否成功，与上一节一步标签的统计层次不同。例如三次尝试费用是 $0.1、0.2、0.6，前两次成功，条件均价是 $0.15，包含失败的每成功成本是 $0.45。二者回答不同问题；成功数为零时都不能给出有限的“每成功成本”。

10. 与行为树、VLA 动作头和后续研究怎样连接

10.1 行为树负责生命周期，Jev 负责一次有限选择

行为树可以管理任务顺序、条件检查、超时与恢复，Jev 成为某个有限选择节点。模型输出映射到已有分支，叶节点继续报告运行、成功或失败。模型的 DONE 应经过局部条件验证后再映射为成功，不能直接跳过父节点的完成条件。

异步行为节点启动操作后先返回 RUNNING，之后的 tick 检查进度；收到停止请求时还需要相应的取消处理。BehaviorTree.CPP 的文档强调不要让长时间阻塞的 tick 卡住整棵树。异步动作节点

据此设计 Jev 节点时，可以让一次启动对应一次请求，而不是每次 tick 都发请求。以下时序只是集成算例：

时刻 / ms发生什么调度器的处理
0当前局部目标为“接近把手”，绑定一次观测并请求选择保存目标版本与请求 ID，节点返回 RUNNING
20、40、60行为树继续 tick，请求还没完成检查取消、超时与已有 future，不重复调用
80上层发现对象识别有误，切换局部目标旧目标版本失效；尝试取消旧请求
140旧请求仍然返回“向前接近”即使置信度很高，也丢弃旧目标的响应
160新观测和新目标已准备好发出新的请求，使用新的绑定关系

取消本地等待不一定能撤回远端已经进行的推理，所以“发过取消”不能代替版本检查。若物理动作已经提交，任务切换还要按控制器协议停止或等待，并确认实际状态；不能只清空 Python 对象，就假设机器人也停下来了。

10.2 用可观测进度限制局部循环

“向前移动成功”通常只说明动作接口执行完毕。对于推门任务，还需要看门的角度或位置是否变化；对于抓取，还需要看物体是否随夹爪稳定运动。这些任务效果可以成为回到上层的条件，而不是一律由 Jev 从自己的上次回答中推断。

例如，给局部委派设置有限时间、动作次数和无进展次数；每次动作后更新实际观测。当达到预算或连续没有可测进展时，结束委派并交回规划。进度阈值应结合传感器误差和任务含义，不能把测量噪声当作正向进展，也不能仅用动作次数认定任务完成。

规划器接收的程序化交接记录至少应说明：原局部目标、实际执行的动作、最后有效观测、进度依据和交接原因。模型提出却未提交的动作留在决策日志中，不混入实际动作历史。这样上层才能区分“抓取失败”“模型没有可用候选”和“动作已执行但结果尚不明确”。

10.3 与连续策略、主动感知及候选学习组合

与 VLA 连接：Jev 可以选择任务阶段或已定义技能，而技能内部使用 VLA 策略。若 VLA 已能稳定直接闭环，额外加入选择层会增加状态压缩与交接误差，是否值得需由对照实验决定。Flow Matching 解决连续动作分布的生成问题；类型化选择解决有限选项的判断问题，它们可以组合，但不是彼此的替代实现。

与主动感知连接：把“移动相机”“等待遮挡消失”“重新识别对象”做成明确候选，可让不确定性触发信息获取。是否真的减少后续错误，仍应比较总完成时间，不能只看某次选择的 confidence 提升。

与学习型候选生成连接：当主要失败来自覆盖不足时，可以改进技能库、可达性估计或候选生成模型，再重新测选择器。这样形成“生成候选—选择—执行—验证”的可拆解流程，也能知道优化发生在哪一层。

10.4 对照 SayCan：有助于任务与能够完成是两种依据

2022 年的 SayCan 已经研究如何让语言模型选择机器人技能：语言侧评估技能与指令的关联，技能对应的价值函数提供当前状态下的执行可行性，两类分数共同参与选择。SayCan 项目与方法说明

用简化记号表示，若技能的语言描述为 lll，任务为 ggg，已有步骤为 hhh，当前状态为 sss，其选择分数结合语言项与技能价值项：

score(l)=pLM(l∣g,h) Vl(s). \mathrm{score}(l)=p_{\mathrm{LM}}(l\mid g,h)\,V_l(s). score(l)=pLM​(l∣g,h)Vl​(s).

前一项回答“这项技能是否有助于当前指令”，后一项提供“这项技能在当前状态下能否成功”的依据。例如需要海绵清理桌面，但海绵还未找到，任务语义可能偏向抓取，而执行可行性会推动系统先寻找。这两项的来源与评估目标不同。

Jev 的 Choice 可以承担有限候选中的语义选择，但返回的概率并没有自动附带一个从机器人交互数据学得的技能价值函数。若研究两者的组合，应明确哪些可行性依据进入状态、哪些条件在程序中检查，再固定技能库和执行器做对照。语言判断、可行性估计和真实完成结果分别记录，才能定位收益来自哪一层。

阅读自测与验收

  1. Jev 是直接接收图像并输出机器人轨迹的 VLA 吗？ 不是；本文讨论的接口接收文本或结构化状态，物理轨迹由其他模块实现。
  2. 类型化输出是否意味着动作一定正确？ 不是；候选覆盖、语义选择和执行结果仍可能出错。
  3. 70–500 ms 能直接证明 2–14 Hz 机器人闭环吗？ 不能；倒数没有计入完整闭环，并不保证尾延迟。
  4. Jev-Mobile 的 73.4% 是否统计了全部失败尝试？ 该数字由成功轨迹平均模型费用计算，不能当成包含失败的每成功成本。
  5. confidence 可以直接用最高选项概率代替吗？ 不可以；应保留字段含义并在自己的数据上验证阈值。
  6. 局部动作方向全部正确，任务就会成功吗？ 不一定；高层目标、接触状态和物体进度反馈仍可能失败。
  7. 脚本通过是否证明 Jev 已完成真机验证？ 不证明；脚本只检查离线协议与路由逻辑。
  8. 请求只用 125 ms，观测就一定新鲜吗？ 不一定；观测年龄应从采集时刻计算，还包括预处理与排队。
  9. 阈值提高，接受部分的错误率一定降低吗？ 不一定；分布变化或分数失准可能让高分段包含更多错误。
  10. 无人通过阈值能报告零错误率吗？ 不能；接受部分为空时，这项错误率未定义。
  11. 总体 ECE 为零能证明每个技能都校准吗？ 不能；汇总可能掩盖子组偏差，也不代表有足够的区分能力。
  12. 行为树每次 tick 都要重新调用 Jev 吗？ 不需要；等待中的异步节点检查已有请求，目标改变后拒绝旧响应。
